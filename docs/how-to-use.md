## ۰. سه سطح استفاده

شما لازم نیست همه‌ی مراحل را بروید. از هر جا که به کارتان می‌آید شروع کنید:

| سطح | نیاز به CANoe | چه کاری می‌دهد | زمان راه‌اندازی |
|---|---|---|---|
| **الف) شبیه‌ساز** | ❌ | تمرین UI، نوشتن سناریو، ساخت تست | ۳۰ ثانیه |
| **ب) CANoe واقعی** | ✅ | تحریک باس، خواندن سیگنال، تست روی restbus | ۱۵ دقیقه (یک‌بار) |
| **ج) CI / بدون رابط** | ✅ | اجرای خودکار تست با گزارش JUnit | ۵ دقیقه بعد از ب |

**توصیه: اول «الف» را انجام دهید.** حتی بدون CANoe می‌فهمید تستر چه می‌کند و سناریوهایتان را آماده می‌کنید.

## الف) حالت شبیه‌ساز — بدون CANoe

روی ویندوز، در پوشه‌ی پروژه:

```
bridge\run_sim.bat
```

یا دستی:

```bash
python bridge/nbcm_bridge.py --sim
```

بعد آدرس `http://127.0.0.1:8771/` را در مرورگر باز کنید.

> در این حالت هیچ چیزی به CANoe وصل نمی‌شود. یک restbus ساختگی داخل پل اجرا می‌شود تا بتوانید
> همه‌ی رفتارها (Timeout، قطع گره، محدوده‌ی سیگنال) را ببینید.

### چه چیزی را امتحان کنید

1. **نوار بالا:** دو نشانگر می‌بینید — `Simulator` (منبع داده) و وضعیت Measurement.
   دکمه‌ی سوم `کنترل: CANoe` است؛ در حالت شبیه‌ساز اثری ندارد.
2. **تب «پنل کنترل»:** «سناریوی رانندگی» را با ▶ روشن کنید. سرعت خودرو شروع به بالا رفتن می‌کند
   و در کارت‌های سیگنال دیده می‌شود.
3. **تب «گره‌ها»:** ۱۳ کارت گره. هر کارت را خاموش کنید → پیام‌های آن گره در پایشگر
   `OFFLINE` می‌شوند (نه `TIMEOUT` — تفاوت مهم است).
4. **تب «تست‌ها»:** دکمه‌ی **▶ اجرای همه** → ۷ تست اجرا می‌شود، چند ثانیه طول می‌کشد.
5. **تب «گزارش»:** نتیجه‌ی همان اجرا + دکمه‌ی چاپ/PDF.

## ب) اتصال به CANoe 12 واقعی

### ب-۱. سه فایل را به CANoe بدهید (یک‌بار برای همیشه)

| کار | مسیر در CANoe 12 | فایل |
|---|---|---|
| متغیرها | `Environment → System Variables → Import` | `canoe/NBCM_Test.vsysvar` |
| پنل | `Home → Panel → Add Panel…` | `canoe/panels/NBCM_Smoke.xvp` |
| نود CAPL | `#include` در نود restbus | `canoe/NBCM_TesterBridge.can` |

برای گام CAPL، در انتهای فایل `NBCM_Full_Restbus_Simulation.can` این خط را اضافه کنید:

```c
#include "NBCM_TesterBridge.can"
```

> چرا همان نود؟ چون پل به متغیرهای CAPL آن فایل دسترسی می‌خواهد.
> اگر نود جداگانه بسازید، متغیرها را نمی‌بیند.

بعد از `Ctrl+S` و **Start** کردن Measurement، در پنجره‌ی **Write** باید ببینید:

```
[TesterBridge] active, namespace NBCM_Test
```

اگر این خط نیامد، ادامه ندهید — مشکل همان‌جاست. `python tools/doctor.py` را اجرا کنید.

### ب-۲. پل را وصل کنید

```bash
python bridge/nbcm_bridge.py --canoe --canoe-config "C:\CANoe\NBCM\NBCM.cfg"
```

یا فایل `bridge\run_windows.bat` را باز کنید و بالای آن مسیر `CANOE_CFG` را درست بگذارید، بعد دوبار کلیک.

پل به CANoe می‌چسبد، Measurement را اگر لازم باشد شروع می‌کند، و تستر را در یک پنجره‌ی جمع‌وجور
کنار CANoe باز می‌کند (`nbcm_window.py`).

### ب-۳. کنترل را به تستر بدهید — **مهم‌ترین قدم**

در نوار بالای تستر، دکمه‌ی **`کنترل: CANoe`** را بزنید تا بشود **`کنترل: تستر`**.

| حالت | چه کسی روی باس می‌نویسد | کِی استفاده کنیم |
|---|---|---|
| `کنترل: CANoe` | restbus خودِ CANoe | وقتی می‌خواهید فقط تماشا کنید |
| `کنترل: تستر` | تستر (از طریق `DRIVE_MODE=1`) | وقتی می‌خواهید سیگنال تزریق کنید |

اگر این را عوض نکنید، هر تغییری در تستر با مقادیر restbus جنگ می‌کند و به باس نمی‌رسد.
این شایع‌ترین دلیل «کار نمی‌کند» است.

### ب-۴. کانال‌ها را تنظیم کنید

تب **«اتصال»** → بخش **نگاشت کانال**: `HS-CAN` و `LS-CAN` را روی شماره‌ی واقعی پروژه‌ی خودتان بگذارید
(پیش‌فرض ۱ و ۲ است، که ممکن است برای شما درست نباشد) → **ذخیره**.

## ج) نوشتن و اجرای تست

### در رابط گرافیکی

1. تب **«تست‌ها»** → هر ردیف یک تست با شناسه، Suite و Verdict.
2. **▶ اجرای همه** / **اجرای انتخاب‌شده** / **اجرای FAILها** — سه دکمه برای سه سناریو.
3. ستون **دلیل** می‌گوید چرا FAIL شد؛ لاگ کامل در پایین صفحه.
4. تب **«گزارش»** → چاپ یا دانلود JSON.

### ویرایش تست‌ها

تب **«سناریوها»** یک JSON ویرایش‌پذیر است. دو دکمه‌ی مهم:

- **اعمال و اعتبارسنجی** — قبل از اجرا چک می‌کند ساختار درست باشد
- **ذخیره محلی** — در `localStorage` مرورگر ذخیره می‌کند (بین اجراها می‌ماند)

اگر خراب شد: **بازگشت به پیش‌فرض**.

ساختار یک تست:

```json
{
  "id": "TC-001",
  "title": "سرعت خودرو روی باس منتشر می‌شود",
  "suite": "Signal",
  "steps": [
    { "set": { "$offline": { "ABS": false } } },
    { "set": { "Hs_Abs_VehicleSpeed": 60 } },
    { "settle": 400 },
    { "expect": { "signal": "Hs_Abs_VehicleSpeed", "op": ">=", "value": 1 } }
  ]
}
```

دستورهای موجود در هر مرحله:

| دستور | کار |
|---|---|
| `set` | مقدار سیگنال را می‌نویسد؛ `$offline` گره را قطع/وصل می‌کند |
| `settle` | چند میلی‌ثانیه صبر می‌کند |
| `expect.signal` + `op` + `value` | شرط روی مقدار سیگنال (`>=`, `<=`, `==`, `!=`, `>`, `<`) |
| `expect.fresh` / `absent` | تازگی یا نبودِ پیام (برای تست Timeout) |

**حلقه‌ی کاری من:** تست را در حالت شبیه‌ساز بنویسید و PASS کنید → بعد به CANoe واقعی وصل کنید.
این‌طور خطای تست‌نویسی را از خطای واقعی DUT جدا می‌کنید.

### از خط فرمان (برای CI)

```bash
python bridge/run_suite.py --suite tests/test_suite.json --take-control ^
    --junit reports/junit.xml --report-dir reports
```

`--take-control` همان کاری را می‌کند که دکمه‌ی `کنترل: تستر` — برای اجرای بدون دخالت انسان لازم است.
خروجی JUnit را هر CI (Jenkins/GitLab) می‌خواند.

خروجی واقعی همین دستور روی شبیه‌ساز (اجرا شد):

```
verdict: PASS   pass=7 fail=0 inconclusive=0 total=7
report : reports/report_RUN-20261118-082917.json
```

### API پل (اگر خواستید از اسکریپت خودتان صدا بزنید)

| متد | مسیر | بدنه | کار |
|---|---|---|---|
| GET | `/api/health` | — | وضعیت: `mode`، `canoe`، `sysvars`، `measRunning`، `driveMode` |
| GET | `/api/state` | — | `frames`، `offline`، `msgAge`، `driveMode` |
| GET | `/api/signals` | — | متادیتا + فهرست ۴۸۱ سیگنال |
| POST | `/api/signal` | `{"signal":"…","value":60}` | نوشتن مقدار (`"raw":true` برای بدون clamp) |
| POST | `/api/offline` | `{"node":"ABS","offline":true}` | قطع/وصل گره |
| POST | `/api/drive` | `{"tester":true}` | دادن کنترل به تستر |
| POST | `/api/measurement` | `{"action":"start"\|"stop"}` | کنترل Measurement |

مثال:

```bash
curl -X POST http://127.0.0.1:8771/api/drive -d '{"tester":true}'
curl -X POST http://127.0.0.1:8771/api/signal -d '{"signal":"Hs_Abs_VehicleSpeed","value":60}'
curl -X POST http://127.0.0.1:8771/api/offline -d '{"node":"ABS","offline":true}'
curl http://127.0.0.1:8771/api/state
```

## عیب‌یابی — به ترتیب بررسی کنید

**۱. اول از همه:**

```bash
python tools/doctor.py
```

این ابزار داده، CAPL، پنل‌ها و اتصال COM را چک می‌کند و دقیقاً می‌گوید کدام لایه خراب است.

**۲. جدول علامت‌ها:**

| نشانه | علت احتمالی | کار |
|---|---|---|
| نشانگر `Simulator` است ولی CANoe باز است | پل با `--canoe` اجرا نشده | با `--canoe` دوباره اجرا کنید |
| پل وصل است ولی سیگنال‌ها عوض نمی‌شوند | `کنترل: CANoe` است | دکمه‌ی کنترل را بزنید |
| همه‌ی پیام‌ها `TIMEOUT` | Measurement اجرا نیست | Measurement را Start کنید |
| یک گره `OFFLINE` است | قبلاً قطع شده | کارت گره را روشن کنید |
| پنل باز می‌شود ولی کنترل‌ها خالی‌اند | System Variables import نشده | ب-۱ را انجام دهید |
| `[TesterBridge]` در Write دیده نمی‌شود | `#include` جای اشتباهی است | باید در همان نود restbus باشد |
| نام سیگنال در تست پیدا نمی‌شود | نام دقیق را اشتباه نوشته‌اید | `canoe/panel_binding_systemvars.csv` را نگاه کنید |

**۳. نام دقیق سیگنال‌ها** در این دو جا هست:

- `canoe/panel_binding_systemvars.csv` — همه‌ی ۴۹۹ متغیر
- تب «گره‌ها» در تستر — با جستجو

## دو نکته که ممکن است اذیتتان کند

**الف) تستر و پنل `.xvp` هر دو یک کار می‌کنند.** تفاوتشان:

- پنل `.xvp` → داخل CANoe، برای تحریک سریع با موس. سناریو و گزارش ندارد.
- تستر HTML → کنار CANoe، برای تست تکرارپذیر و مستندسازی.

هر دو از یک قرارداد (`NBCM_Test::<Signal>`) استفاده می‌کنند، پس هم‌زمان هم می‌شود.

**ب) `SCENARIO_RUNNING` را دستی صفر نکنید** وقتی سناریو در حال اجراست — تستر خودش مدیریتش می‌کند.
اگر گیر کرد، در تب «پنل کنترل» دکمه‌ی **ریست** کنار «سناریوی رانندگی» را بزنید.
